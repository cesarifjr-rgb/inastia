Les 27 routes du sitemap ont été parcourues dans Chrome : statut HTTP 200, titre unique, H1, description, canonical, hreflang appropriés, métadonnées Open Graph, images chargées avec texte alternatif, absence d’erreur console/runtime et de débordement horizontal. Les liens internes et fragments ont été vérifiés. L’accueil passe aussi à 320, 375, 768, 1024, 1440 et 1920 px.

Les scans contextuels portent sur l’accueil, le guide déplié sans choix, chacun des quatre résultats du guide, la photographie en dialogue, les trois services, la présentation, l’audit, le contact initial et avec cinq erreurs inline, les trois pages légales et la page 404, à 390 et 1440 px. Les fichiers `axe/*.json` contiennent les rapports complets et les PNG correspondants.

Les parcours communs Chrome/Firefox/WebKit vérifient le menu mobile au clavier, son état inert et le retour du focus après Échap ; la navigation desktop ; le choix radio avec Espace puis flèche ; le résultat et l’intention transmis au formulaire ; le dialogue avec Précédent/Suivant/Échap et retour du focus ; les erreurs inline, leurs associations et leur correction. La validation est interceptée et les fournisseurs externes sont bloqués. Aucun test de compatibilité n’émet de requête de contact réelle.

La suite Chrome conserve les huit anciens cas de mouvement, adaptés aux illustrations actuelles, et ajoute sept cas natifs. Elle contrôle les transformations et temps des animations CSS, la pause sans perte de phase, la reprise clavier, la réduction des mouvements au chargement et après changement système, les illustrations hors écran, les révélations après défilement/redimensionnement, le focus et l’absence de contenu masqué. L’entrée de l’atlas est unique ; aucune requête GSAP, modèle 3D ou worker et aucun canvas n’est observé. Deux tests confirment une vraie restauration BFCache dans Chrome avec identifiant de document conservé et `pageshow.persisted`. Le masquage du document est testé par une simulation de `document.hidden` et de `visibilitychange`, pas par un changement natif d’onglet.

Le comportement sans JavaScript est couvert sur desktop et mobile : contenu, comparaison des services, FAQ, liens vers les photographies, navigation et contacts directs. L’atlas décoratif est volontairement absent de la disposition mobile. Le test ancien qui attendait le SVG hospitality supprimé vérifie maintenant ce comportement ainsi que le titre et le CTA ; les assertions de navigation et de contact restent présentes. Les sélecteurs de liens ont été précisés pour éviter les recommandations masquées du guide. Aucun seuil de validation n’a été assoupli.

Deux écarts de CSS ont été corrigés pendant l’intégration : le reset de réduction des mouvements supprimait les animations au lieu de les mettre en pause ; l’espacement du contact plaçait le sélecteur d’intention à 610,59 px sur mobile, au-delà du seuil existant de 600 px. La règle CSS et l’espacement ont été corrigés ; les tests correspondants passent. Les guards d’initialisation des modules contact, orientation et portfolio sont présents. La suite vérifie notamment l’absence de double envoi pendant une requête et les traversées répétées de l’historique.

Le premier passage WebKit sur HTTP local n’était pas exploitable : le header CSP `upgrade-insecure-requests` transformait les URLs de CSS, JavaScript, fontes et SVG en HTTPS sur le port HTTP 4100 ; ces cinq ressources échouaient avec `SSL connect error`. Le même build et les mêmes headers ont ensuite été testés derrière un proxy TLS éphémère sur `127.0.0.1:4143`. Les huit cas WebKit et les huit cas Firefox passent alors. Les quatre captures HTTPS de succès n’ont aucune requête échouée ; les fontes Manrope et le moteur de mouvement sont chargés. La CSP de production est inchangée, aucune autorité de certification n’a été installée dans Windows ; seule la vérification du certificat local autosigné a été ignorée dans le contexte de test. Le proxy a été arrêté après les vérifications.

Les APIs retenues correspondent aux contrats documentés : `showModal()` place le dialogue dans la couche supérieure et rend le reste du document inerte ; `HTMLElement.inert` sert au menu ; Intersection Observer suit la visibilité sans boucle permanente de défilement. Sources consultées : [MDN showModal](https://developer.mozilla.org/en-US/docs/Web/API/HTMLDialogElement/showModal), [MDN inert](https://developer.mozilla.org/en-US/docs/Web/API/HTMLElement/inert), [MDN Intersection Observer](https://developer.mozilla.org/en-US/docs/Web/API/Intersection_Observer_API). La compatibilité est étayée par les parcours exécutés ci-dessus, pas déduite uniquement de la documentation.

Les résultats axe ne constituent pas une certification WCAG exhaustive. Les seuls items `incomplete` concernent le contraste de symboles et de chiffres SVG trop courts pour l’heuristique. L’échantillonnage des couleurs CSS sur l’accueil donne 9,52:1 pour les chiffres de l’atlas et la flèche, 5,32:1 pour le symbole de pause, 6,80:1 pour la coche et 5,46:1 pour les étoiles ; ces mesures sur fonds CSS pleins ne remplacent pas une inspection de chaque pixel. Le lecteur d’écran, les appareils physiques, la livraison réelle d’email, les métriques terrain INP et la performance Lighthouse finale ne font pas partie de cette revue.
